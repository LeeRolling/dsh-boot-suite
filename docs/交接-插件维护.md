## 4. 发布流程（照做）

1. 改 `package.json` 版本 + `lib/client.js` 的 `FALLBACK_VERSION`。
2. 写 CHANGELOG。
3. `npm test`（必须 0 失败；坐标规范 196 层）。
4. `npm run release`（构建并双重校验 BOM/JSON/关键文件）。
5. 复制版本化包：`dsh-boot-suite-win-V<版本>.zip`。
6. `gh release create v<版本> <固定包> <版本化包> --repo LeeRolling/dsh-boot-suite --title ... --notes-file ...`（已存在则 `gh release upload --clobber`）。
7. 用 `gh api repos/LeeRolling/dsh-boot-suite/releases/tags/v<版本>` 验证两个资产都在。
8. 本地 `git add -A && git commit`；`git push` 若能连上就推，不能就看第 6 节。

## 5. 自动更新机制（当前实现）

1. 用户点【立即更新】→ 宿主让 Chrome 打开**版本化资产** URL。
2. 宿主监听 Downloads/Desktop/.dsh/downloads，接住 zip 并复制到 `~/.dsh/boot-suite-updates/<版本>.zip`。
3. 弹窗确认 → 启动外部更新器（黑色 PowerShell 窗口）。
4. 更新器提示用户**手动完全退出 DSH**；检测到退出后解压、清理 package.json BOM、跑安装器、自动重开 DSH。
5. 失败写桌面日志 + 恢复配置备份。

关键点：不能从 DSH 内部“自动关闭并替换自己”，所以必须手动退出；这是设计，不是 bug。

补充（2026-10-25 实测）：
- 更新器窗口最多等 **15 分钟**（`tools/update-apply.ps1` 里 `AddMinutes(15)`）。若本机验证时用户没在 15 分钟内退出 DSH，会超时取消（桌面日志停在启动 3 行）；需要更长就复制脚本改等待时间。
- **不要用外部自动化“生成 EncodedCommand 启动器再执行更新脚本”**：Windows Defender 的 FileFix 启发式会把这种“脚本生成脚本再执行”的命令行误判为 `Trojan:Win32/FileFix.BBA!MTB`（检测资源是 CmdLine，不是文件；插件包哈希不变），并可能直接杀掉更新器。安全做法：把官方 zip 解压到 `~/.dsh/boot-suite-updates/<版本>/pkg`，写一个只调用 `pkg\tools\install.ps1` 的纯文本 .cmd，让用户完全退出 DSH 后双击（2026-10-25 就是这样装上的）。

## 6. GitHub push 被墙的同步办法

- `git push` 会 443 超时；`gh api` 可通。
- 需要同步时：用 GitHub API 创建 blob/tree/commit 并 PATCH `refs/heads/main`（之前做过，脚本模式见 git 历史/本会话记录）。
- Release 资产始终用 `gh release upload`（API 通）。
